# Технічні концепції

Цей документ пояснює основні концепції та розрахунки, що використовуються компонентом SunAllocator.

## Розрахунок надлишкової потужності

Сенсор `sun_allocator_excess_power` розраховує невикористаний потенціал потужності, яку можна отримати від сонячної панелі. Розраховується за формулою:

```
надлишок_потужності = розрахункова_макс_потужність_при_поточній_напрузі - поточна_вихідна_потужність_ФЕМ
```

Це значення показує, скільки додаткових ватів можна отримати від панелі при її поточній робочій напрузі. Коли це значення велике, це свідчить про те, що панель має значний невикористаний потенціал, який можна задіяти за допомогою додаткових навантажень.

## Розуміння MPPT та роботи сонячних панелей

Сонячні панелі мають характеристичну криву I-V (струм-напруга), яка визначає їхню вихідну потужність. Ключові моменти для розуміння:

1.  **Точка максимальної потужності (MPP)**: Це оптимальна робоча точка, де добуток напруги та струму є максимальним. Вона відповідає конкретним значенням напруги (Vmp) та струму (Imp).

2.  **Робочі зони**:
    *   **Нижче Vmp**: У цій зоні панель працює зі відносно постійним струмом. Зі збільшенням напруги потужність зростає приблизно лінійно.
    *   **При Vmp**: Це оптимальна робоча точка з максимальною вихідною потужністю.
    *   **Вище Vmp**: У цій зоні струм різко падає зі збільшенням напруги, що призводить до зниження потужності.

3.  **Індикатор можливого надлишку**: Атрибут `excess_possible` має значення `true`, коли напруга панелі перевищує Vmp. Це свідчить про:
    *   Панель працює в зоні постійної напруги (вище Vmp).
    *   Вихідна потужність, ймовірно, менша за оптимальну.
    *   Контролер MPPT потенційно може збільшити потужність, знизивши напругу до Vmp.

4.  **Чому зазвичай «false»**: Більшість сонячних систем з контролерами MPPT працюють при напрузі Vmp або нижче для максимізації потужності, тому `excess_possible` зазвичай має значення «false» під час нормальної роботи.

## Розрахунок максимальної потужності на основі MPPT

Значення `current_max_power` оцінює максимальну потужність, яку можна отримати при поточній напрузі, на основі принципів відстеження точки максимальної потужності (MPPT). Це допомагає зрозуміти:

1.  Яку потужність ваша панель потенційно може виробляти при поточній робочій напрузі.
2.  Чи працюєте ви поблизу оптимальної напруги для максимальної потужності.
3.  Яку додаткову потужність можна отримати при оптимальному керуванні MPPT.

#### Технічні деталі алгоритму MPPT

SunAllocator використовує вдосконалену модель для оцінки максимально можливої потужності при будь-якій напрузі:

1.  **Розрахунок відносної напруги**:
    ```
    # Послідовне з'єднання: напруги панелей підсумовуються
    відносна_напруга = виміряна_напруга_ФЕМ_В / (номінальна_Vmp_панелі_В * кількість_панелей_послідовно)

    # Паралельне з'єднання: напруга однакова для всіх панелей
    відносна_напруга = виміряна_напруга_ФЕМ_В / номінальна_Vmp_панелі_В
    ```
    Значення `1.0` означає, що масив працює точно в точці максимальної потужності (Vmp).

2.  **Модель оцінки потужності**:
    *   Для напруги нижче або рівної Vmp (`відносна_напруга ≤ 1.0`):
        ```
        # Поліноміальне наближення: плавний підйом до Vmp,
        # відповідає зоні постійного струму реальної кривої I-V.
        оцінкова_макс_потужність_Вт = номінальна_Pmax_панелі_Вт * (
            відносна_напруга * (1.0 - 0.1 * (1.0 - відносна_напруга))
        )
        ```

    *   Для напруги вище Vmp (`відносна_напруга > 1.0`):
        ```
        # Квадратичне падіння: потужність різко знижується після Vmp,
        # відображає стрімке зменшення струму в зоні постійної напруги.
        оцінкова_макс_потужність_Вт = номінальна_Pmax_панелі_Вт * max(
            0,
            1 - 1.5 * (відносна_напруга - 1) ** 2
        )
        ```

3.  **Конфігурація панелей**:
    Алгоритм враховує різні схеми з'єднання панелей:
    *   **Послідовне (Series)**: Напруга підсумовується, струм залишається незмінним.
    *   **Паралельне (Parallel)**: Струм підсумовується, напруга залишається незмінною.

## Алгоритм розподілу потужності

Цей розділ описує, як SunAllocator вирішує, які пристрої вмикати та скільки потужності виділяти кожному.

### Крок 1 — Розрахунок надлишкової потужності

Щоразу, коли сенсор потужності ФЕМ оновлюється, SunAllocator розраховує, скільки потужності доступно для розподілу:

```
# За замовчуванням (без сенсора споживання будинку):
# надлишок = НЕВИКОРИСТАНИЙ запас на кривій панелей, мінус резерви.
невикористаний_Вт      = оцінкова_макс_потужність_при_поточній_напрузі_Вт - поточна_потужність_ФЕМ_Вт
надлишок_потужності_Вт = невикористаний_Вт
                       - власне_споживання_інвертора_Вт   # з налаштувань інтеграції
                       - зарезервована_потужність_АКБ_Вт  # з налаштувань інтеграції
```

`невикористаний_Вт` додатний **лише коли напруга масиву вище точки максимальної потужності
(Vmp)** — тобто інвертор придушує панелі, бо ніхто не споживає надлишок. SunAllocator
пропонує пристроям тільки те, що панелі реально можуть додати понад поточну продукцію.
(Поблизу напруги холостого ходу ця оцінка приблизна — освітленість там напряму не
спостерігається — тому значення демпфується, щоб уникнути стрибків.)

Окремого «паралельного» режиму немає. Налаштування **сенсора споживання будинку** просто
*уточнює* ту саму MPPT-оцінку, додатково обмежуючи її реальним виміряним споживанням, що
точніше:

```
# З сенсором споживання будинку (точніше):
надлишок_потужності_Вт = min( невикористаний_Вт,
                              оцінкова_макс_потужність_Вт - споживання_будинку_Вт - використаний_заряд_АКБ_Вт )
                       + надлишок_заряду_понад_резерв_Вт
```

Резерв батареї ділиться на захищену частину (`min(заряд, резерв)`) і заряд понад резерв, який
стає доступним пристроям. Резерв модулюється порогом **Ділитись надлишком вище SOC** (нижче
нього батарея забирає все). Від'ємний або нульовий результат означає, що нічого не вмикається.

### Метод розрахунку (mppt · mppt_probe · export)

Формула вище — це метод **`mppt`** (за замовчуванням). Селектор **Метод розрахунку надлишку**
(Розширені налаштування) дозволяє підлаштувати оцінку під топологію інвертора:

- **`mppt` (обережний, дефолт)** — розрахунок невикористаного запасу, описаний вище. Безпечний,
  але *занижує* доступну сонячну на гібридному інверторі що слідує за навантаженням, коли
  батарея на стелі заряду, а споживання низьке: інвертор тоді **куртейлить** панелі під
  навантаження, тож `pv_power` йде за споживанням, а модель читає куртейлений вихід як «мало
  сонця». Атрибут `curtailment_detected` сигналізує коли це відбувається (є запас, батарея не
  розряджається, батарея не приймає заряд).

- **`mppt_probe` (MPPT + активний підбір)** — публікує те саме обережне значення, що й `mppt`,
  плюс контролер що повертає куртейлену енергію, яку оцінка не бачить. Коли виявлено куртейлінг
  і пристрій чекає лише на більше потужності, probe нарощує невеликий бюджет *headroom*, щоб
  алокатор увімкнув пристрій, і стежить за батареєю: якщо батарея лишається без розряду — додане
  навантаження було вільним (покрите раніше куртейленим PV) і бюджет росте далі; якщо батарея
  пішла в розряд — навантаження не вільне, бюджет відкочується нижче того рівня + cooldown не дає
  негайно повторити (щоб on/off-пристрій типу компресора AC не циклувався). Пріоритет, часткове
  заповнення і min-пороги обробляє звичайний алокатор через збільшений бюджет. «Батарея на стелі
  заряду» визначається за *потужністю* заряду близькою до нуля, **а не за SOC** — багато
  інверторів капають заряд нижче 100 %.

- **`export` (енергобаланс)** — для інверторів з **експортом у мережу**, де `pv_power` відображає
  справжню генерацію, а не вихід під навантаження. Надлишок — прямий енергобаланс:
  ```
  надлишок_Вт = pv_power_Вт - споживання_будинку_Вт - власне_споживання_інвертора_Вт
              - зарезервований_заряд_АКБ_Вт
  ```
  Заряд батареї понад резерв перетікає у доступний надлишок. Цей метод не використовує MPPT I-V
  криву (сенсори кривої лишаються лише як діагностика).

**Опційно: probe, керований прогнозом.** Якщо задати **Сенсор прогнозу PV** (Налаштування —
напр. Forecast.Solar чи Open-Meteo, об'єднані в одну сутність для масивів з кількома скатами), probe
використовує прогноз як **ціль** зростання замість сліпого підбору: нарощує headroom до
`forecast − pv_power`, закриваючи близько 25 % залишку розриву за тік, і батарея валідує кожен крок
так само, як вище — розряд *до* досягнення цілі означає, що прогноз був завищений, тож бюджет
відкочується нижче того рівня й слідує cooldown (фактично — недовіра прогнозу, доки той не
відновиться). Прогноз також вмикає таке probe-зростання у обережному методі `mppt`; там відновлений
headroom живить лише **спекулятивний** бюджет, який можуть споживати пристрої з увімкненим *Дозволити
спекулятивний надлишок*, тож opt-out навантаження (напр. кондиціонер, який не варто смикати) завжди
лишаються на чистому обережному надлишку. Опубліковане значення `excess_power` прогноз **ніколи** не
підіймає — воно проявляється лише через діагностичні атрибути `forecast_potential_w`,
`forecast_untapped_w` та `probe_headroom_w`.

**Опція для кожного пристрою.** Чи може пристрій споживати цей спекулятивний headroom — це
налаштування на кожен пристрій, *Дозволити спекулятивний надлишок* (`allow_probe`, Розширені
налаштування). Доступний надлишок ділиться на два пули: **реальний** пул (обережний надлишок —
справді доступний, доступний усім пристроям) і **додатковий** пул (headroom, знайдений
probe/прогнозом, понад це). Пристрої з вимкненим *Дозволити спекулятивний надлишок* беруть лише з
реального пулу, тож навантаження, яке ніколи не варто ганяти спекулятивно (напр. компресор
кондиціонера), завжди працює лише на обережному надлишку.

### Захист за SOC батареї

Захист батареї має **дві незалежні осі**, що діють у різних фазах батареї, плюс глобальний поріг.
Усі пороги опційні (0 вимикає осі на кожен пристрій; глобальний поріг і поріг ділення також 0 =
вимкнено).

- **СТАРТ (сторона заряду)** — на кожен пристрій `start_battery_soc`. Пристрій може **стартувати**
  лише коли SOC ≥ цього значення. Це гейтить лише нові старти; пристрій, що вже працює, стартовим
  гейтом ніколи не вимикається.

- **СТОП (сторона розряду)** — на кожен пристрій `stop_battery_soc`. Поки батарея
  **розряджається**, працюючий пристрій примусово **вимикається**, коли SOC < цього значення. Він
  ніколи не спрацьовує, поки батарея заряджається або нейтральна, тож навантаження лишається
  увімкненим, доки сонце його ще покриває. Два особливі значення:
  - **0** — успадкувати глобальний поріг `battery_protection_soc`. Окремого стоп-правила на пристрій
    немає; пристрій може розряджати батарею аж до глобального порогу.
  - **100** (за замовчуванням) — ніколи не розряджати батарею для цього пристрою.
  - Будь-яке інше значення має бути **≥** глобального порогу захисту й **перевіряється при
    збереженні** (ненульове значення нижче порогу відхиляється, а не мовчки приймається; `0`
    звільнене від цієї перевірки).

- **Абсолютний поріг** — глобальний `battery_protection_soc`. Нижче нього **кожен** керований
  пристрій примусово вимикається незалежно від напрямку заряду. Ненульовий `stop_battery_soc` на
  пристрій має бути на рівні цього порогу або вище (перевіряється при збереженні); `0` звільнене й
  просто успадковує його.

- **Ділення надлишком** — глобальний `battery_sharing_soc` («Ділитись надлишком вище SOC»). Нижче
  нього батарея зберігає абсолютний пріоритет заряду (надлишок тримається на 0); на цьому рівні або
  вище надлишок ділиться з пристроями.

Смуга **гістерезису** 2 % навколо кожного порогу запобігає смиканню на межі. «Розряд» зараховується
лише коли чиста віддача батареї перевищує `battery_discharge_tolerance_w` (за замовчуванням **20 Вт**),
тож незначний джитер — поки сонце ще покриває навантаження й батарея приблизно нейтральна — не скидає
працююче навантаження.

### Крок 2 — Фільтрація пристроїв

Перед тим як пристрій буде розглянуто для розподілу, він повинен пройти кілька перевірок:

- **Автокерування увімкнено**: Обробляються лише пристрої з увімкненим автокеруванням.
- **Сутність існує**: Керована сутність HA повинна бути доступна в Home Assistant.
- **Перевірка розкладу**: Якщо у пристрою є розклад, поточний час повинен знаходитися в дозволеному вікні. Якщо пристрій наразі увімкнено, але поза розкладом, він негайно вимикається.
- **Шаблон check_usable**: Якщо у пристрою є шаблон `check_usable`, він повинен повертати істинне значення; інакше пристрій вважається непридатним і вимикається. (Зламаний шаблон працює «fail-open» — пристрій вважається придатним, а в журнал пишеться попередження.)
- **Ручне керування**: Ручне перемикання (див. нижче) обробляється *перед* фільтрами розкладу та check_usable і **перевизначає обидва** — лише захист за SOC батареї може примусово вимкнути пристрій, увімкнений вручну.

Пристрої, що не пройшли будь-яку перевірку, пропускаються, а причина фільтрації зберігається для діагностики.

### Крок 3 — Визначення стану пристрою (рішення увімкн./вимкн.)

Для кожного придатного пристрою розподільник вирішує, чи повинен він бути активним, використовуючи порогові значення гістерезису:

```
# Поріг вмикання: пристрій активується, коли надлишку достатньо для його мінімального споживання
поріг_вмикання_Вт  = мінімальне_очікуване_споживання_Вт     # напр. 500 Вт для тепл. підлоги

# Поріг вимикання: пристрій залишається увімкненим, поки потужність не впаде нижче цього рівня
# (зазор гістерезису запобігає мерехтінню при коливаннях сонячної генерації)
поріг_вимикання_Вт = мінімальне_очікуване_споживання_Вт - глобальний_гістерезис_Вт  # напр. 500 - 40 = 460 Вт
```

- **Увімкнути**: якщо `надлишок_Вт >= поріг_вмикання_Вт` І пристрій раніше був вимкнений.
- **Залишити увімкненим**: якщо `надлишок_Вт >= поріг_вимикання_Вт` І пристрій раніше був увімкнений.
- **Вимкнути**: якщо `надлишок_Вт < поріг_вимикання_Вт`.

Це запобігає швидкому циклічному перемиканню увімкн./вимкн., коли сонячна потужність коливається навколо порогового значення.

**Антидребезг**: Зміна стану не застосовується негайно. Пристрій переходить у стан-кандидат і змінює стан лише після того, як налаштований час антидребезгу минув без зміни стану-кандидата.

### Крок 4 — Мінімальний час роботи та стартовий захисний період

Для захисту приладів (компресорів, теплових насосів, насосів) від частого перемикання:

- **Мінімальний час роботи**: Після ввімкнення пристрій залишається ввімкненим щонайменше `min_on_time` секунд, навіть якщо потужність падає нижче порогу вимкнення.
- **Стартовий захисний період**: Коли пристрій вперше вмикається, він отримує додатковий захисний часовий проміжок в 90 секунд для того аби MPPT встиг отримати найвищу точку напруги (в цей час можливе часткове споживання з акумулятору та/або мережі).

### Крок 5 — Розподіл потужності

Кожен пристрій керується в одному з двох **режимів керування**, який обирається для кожного пристрою
при виборі його сутності (селектор сутностей пропонує рядок `(Switch)` для увімкн./вимкн. і рядок
`(Dimmer)` для пропорційного):

- **Увімкн./вимкн.** — пристрій або повністю увімкнено, або повністю вимкнено. Це охоплює звичайний
  перемикач HA, кліматичну сутність, або ESPHome-реле, кероване увімкн./вимкн. через його селектор
  режиму (`On` / `Off`).
- **Пропорційний** — пристрій модулюється між мінімумом і стелею. Це або димована лампа HA, керована
  через її яскравість (`light.turn_on` з `brightness`), або ESPHome-реле, кероване через його селектор
  режиму, встановлений на `Proportional`, плюс яскравість. (Це замінює старіший поділ на типи
  пристроїв «стандартний vs кастомний ESPHome» — можливість тепер обирається режимом керування, а не
  типом пристрою.)

Пристрої сортуються за **пріоритетом** (спочатку найвищий). Розподільник перебирає їх і призначає потужність із залишкового бюджету:

#### Пристрої увімкн./вимкн.

Кожному активному пристрою увімкн./вимкн. виділяється рівно `min_expected_w` з бюджету:

```
# Пристрій отримує рівно своє мінімальне номінальне споживання
виділена_потужність_Вт      = мінімальне_очікуване_споживання_Вт  # напр. 500 Вт
залишковий_сонячний_бюджет -= виділена_потужність_Вт
```

Якщо залишкової потужності недостатньо для пристрою, він вимикається.

#### Пропорційні пристрої

Пропорційна ціль розраховується на основі доступної потужності та максимальної ємності пристрою:

```
# Яку частку потужності пристрою може забезпечити поточна сонячна генерація?
цільовий_відсоток = обмежити(
    5%,    # мінімум: не опускатись нижче 5% (уникає мерехтіння)
    90%,   # максимум: обмеження для запасу безпеки
    (залишковий_сонячний_бюджет_Вт / максимальне_очікуване_споживання_Вт) * 100%
)

# Реальна спожита потужність при цьому відсотку
фактично_спожито_Вт = min(залишковий_сонячний_бюджет_Вт, максимальне_очікуване_споживання_Вт * цільовий_відсоток / 100%)
```

**Стратегії розподілу** (налаштовуються в розширених налаштуваннях):
- **Послідовне заповнення (Fill one by one)**: Кожен пристрій (спочатку з найвищим пріоритетом) отримує стільки, скільки потребує. Залишкова потужність переходить до наступного пристрою.
- **Рівномірний розподіл (Distribute evenly)**: Доступна потужність розподіляється пропорційно між усіма активними пропорційними пристроями на основі їхнього `max_expected_w`.

### Крок 6 — Застосування стану до сутностей

Після прийняття всіх рішень розподільник викликає служби HA:

| Пристрій / Умова | Виклик служби HA |
|-|-|
| Перемикач / освітлення увімкн./вимкн. → увімкнути | `switch.turn_on` / `light.turn_on` |
| Кліматичний пристрій → увімкнути | `climate.set_hvac_mode` з налаштованим режимом HVAC |
| ESPHome-реле увімкн./вимкн. → увімкнути | селектор режиму → `On` |
| Будь-який пристрій → вимкнути | відповідний `turn_off` / `set_hvac_mode: off` / селектор режиму → `Off` |
| Пропорційний (димована лампа) → встановити рівень | `light.turn_on` з параметром `brightness` |
| Пропорційний (ESPHome-реле) → встановити рівень | селектор режиму → `Proportional`, потім яскравість |

Розподільник перевіряє **фактичний стан сутності HA** перед відправкою команди. Якщо сутність вже знаходиться в бажаному стані, виклик пропускається для уникнення зайвого трафіку.

### Крок 7 — Оновлення сенсорів

Після обробки розподільник зберігає результати в спільній пам'яті та надсилає сигнал диспетчера. Сенсор `sun_allocator_power_distribution` отримує цей сигнал і оновлює свій стан та атрибути поточними даними розподілу для всіх пристроїв.

---

## Сторожовий таймер (Watchdog)

Сторожовий таймер відстежує, чи надходять оновлення від сенсора потужності ФЕМ. Якщо протягом налаштованого тайм-ауту оновлень не надходить:

1. Всі керовані пристрої вимикаються (захисне відключення).
2. Попередження записується до журналу.
3. Автокерування автоматично відновлюється, як тільки сенсор починає знову надавати дані.

Тайм-аут за замовчуванням — **3 хвилини** (налаштовується через `WATCHDOG_STALE_AFTER_MINUTES` у `core/settings.py`).

---

## Стани пристрою (Device Status)

ENUM-сенсор `device_status` на кожен пристрій показує поточний стан керування. Можливі значення:

| Стан | Значення |
|---|---|
| `active` | Пристрою виділено потужність (>0 Вт), вважається ввімкненим. |
| `idle` | Реле скомандовано на ON, але сенсор фактичної потужності підтверджує споживання нижче порогу (напр. бойлер досяг цільової температури і елемент вимкнувся). |
| `insufficient_power` | Надлишкова потужність нижча за `min_expected_w` пристрою. |
| `debouncing_on` | Пристрій кандидат ON, але ще в межах debounce-вікна. |
| `debouncing_off` | Пристрій зараз ON, але кандидат впав — очікується вимкнення. |
| `auto_control_off` | Світч авто-керування (або прапорець у конфіг) ВИМКНЕНО. |
| `manual_active` | Користувач вручну **увімкнув** пристрій при увімкненому авто-керуванні; розподільник тримає його увімкненим і зараховує його споживання до бюджету («Manual (on)»). |
| `manual_override` | Користувач вручну змінив стан сутності (ручне **вимкнення**, або увімкнення, що тримається в очікуванні під час звірки); авто-керування для пристрою призупинене. Вибір «липкий» — див. нижче. |
| `filtered` | Пристрій виключено з циклу: поза розкладом, непридатний (шаблон), сутність недоступна, або непідтримуваний домен. Атрибут `refusal_reasons` містить причину. |
| `trying_on` / `trying_off` | Команда надіслана, але сутність не змінила стан; повторюється кожні 30 с, до `RETRY_MAX_ATTEMPTS` (за замовчуванням 3). |
| `failed_on` | Після `RETRY_MAX_ATTEMPTS` команда ON визнана невдалою; користувач отримує persistent_notification. |

## Ручне керування (Manual Control)

Якщо стан сутності змінюється поза командами розподільника (наприклад, ви натискаєте перемикач у Lovelace) при увімкненому авто-керуванні, розподільник запам'ятовує цей вибір і робить його **липким** — **тайм-ауту немає**:

- Ручне **УВІМКНЕННЯ** тримається увімкненим, а його споживання зараховується до бюджету (тож інші авто-пристрої бачать реальний залишковий надлишок); сенсор `device_status` показує `manual_active`.
- Ручне **ВИМКНЕННЯ** лишається вимкненим — авто-керування його не увімкне знову; сенсор `device_status` показує `manual_override`.

Ручний вибір **перевизначає** вікно розкладу **та** шаблон `check_usable`: поки він діє, пристрій ігнорує обидва. Єдине, що може примусово вимкнути пристрій, **увімкнений вручну**, — це **захист за SOC батареї** (стоп-поріг з боку розряду або абсолютний поріг захисту).

Окрім перемикача **«Автокерування»** на кожен пристрій, кожен керований пристрій має на картці
пристрою SunAllocator окрему сутність **«Перемикач»**. Це проксі, яке напряму перемикає керовану
сутність і віддзеркалює її поточний стан, тож ви можете керувати навантаженням, не виходячи з картки
SunAllocator. Перемикання цього **«Перемикача»** при увімкненому автокеруванні поводиться так само,
як ручне перемикання самої сутності: воно реєструється як «липке» ручне перевизначення
(`manual_active` для ручного увімкнення) і підпорядковується всім правилам вище.

Липкий ручний стан зберігається, доки не станеться одне з:

1. світч авто-керування перемкнено **вимкн. → увімкн.** (це відновлює нормальне автоматичне керування), або
2. настає **зміна календарного дня** за локальним часом (вибір скидається опівночі), або
3. спрацьовує **захист за SOC батареї** (лише для ручного увімкнення).
